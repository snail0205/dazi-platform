# 城市「搭子」组局平台 —— 技术选型与架构设计

> 配套：《需求文档》v0.9、《数据库 DDL》、《核心接口清单》。
> 形态：**模块化单体（Modular Monolith）** 起步，为后续按域拆分预留边界。

---

## 1. 选型原则

1. **生态成熟优先**：Java 后端 + uni-app 前端均选用社区最大、文档最全、教程最多的组合，降低学习与招聘成本；
2. **先单体后拆分**：第一版不做微服务/分布式事务，用“模块化 + 事件驱动 + 幂等”解决一致性；
3. **金额与名额是硬约束**：支付、退款、名额扣减全部设计为幂等操作；
4. **配置可热更**：信用规则、退款策略、抽佣比例等业务规则全部落库配置（`platform_config`/`credit_rule`），不写死在代码里。

## 3. 后端工程结构（Maven 多模块，模块化单体）

```
dazi-platform/
├─ docker-compose.yml · .env.example · README.md
├─ docs/                        # PRD / DDL / 接口清单
├─ backend/
│  ├─ pom.xml                   # 父 POM（依赖版本统一管理）
│  ├─ dazi-common/              # 枚举/常量/统一Result/错误码/异常/工具
│  ├─ dazi-framework/           # Sa-Token配置、全局异常、幂等AOP、审计AOP、请求日志
│  ├─ dazi-infra/               # Redis/Redisson/MQ/OSS/短信/微信客户端 自动配置
│  ├─ dazi-module-user/         # auth / user / tags / credit / punishment
│  ├─ dazi-module-activity/     # category / activity / booking / waitlist / evaluation
│  ├─ dazi-module-payment/      # pay / refund / settle / 回调处理
│  ├─ dazi-module-chat/         # WebSocket / 消息 / 已读
│  ├─ dazi-module-admin/        # staff / role / audit / dashboard / config
│  └─ dazi-bootstrap/           # 启动模块（聚合依赖，唯一 main）
├─ mobile-app/                  # uni-app (Vue3+TS) —— C端
└─ admin-web/                   # Vue3 + Element Plus —— 运营端
```

分层约定（每个 module 内）：`controller → service → mapper`；DO（数据库实体）/ VO（对外）/ DTO（入参）/ BO（领域）分离，禁止 DO 直接出参。

模块间调用策略：跨模块先走**领域服务接口（本地调用）**；必须解耦的事件（如“报名成功 → 通知/信用/结算”）通过 **Spring 事件 + RabbitMQ** 异步处理：

```
booking 模块
   ├─ 本地事务提交：member/pay_order/activity.member_count
   └─ 发布事件 JoinConfirmedEvent
        ├─ fanout → notification 服务（站内+订阅消息）
        ├─ topic  → credit 服务（出席累计等）
        └─ topic  → settle 服务（收费局结算单）
```

## 4. 关键机制设计

### 4.1 认证与权限
- C 端：微信 `code2session` 换 openid → 签发 `accessToken(2h)+refreshToken(14d)`，Sa-Token 存储于 Redis，支持服务端吊销；
- 运营端：账号密码（BCrypt）+ 图形验证码；RBAC = `staff→role→permission`；接口用 `@SaCheckPermission("activity:audit")`；
- 关键写操作幂等：`Idempotency-Key` 请求头 → Redis 记录 key+结果（TTL 24h），重复请求直接返回首次结果。

### 4.2 名额扣减与候补（并发正确性核心）
```
① 准入（Redis Lua）：SLOT:act:{id} 计数 +1，若 > slots 拒绝 —— 承压且防刷
② 落库（DB 原子，最终一致权威）：
   UPDATE activity SET member_count = member_count + 1
    WHERE id = ? AND member_count < slots AND status IN (2,3)
   影响行数 = 0 → 回滚并补偿 Redis 计数（-1），抛“名额已满”
③ 唯一约束兜底：activity_member(activity_id, user_id) 唯一
④ 取消/退款 → 名额 -1 → 触发候补第一位（延迟 15min 未支付则顺延）
⑤ 对账 Job（每小时）：Redis 计数 vs DB member_count，异常自动校准
```
> 双写不一致只可能出现在进程崩溃窗口，由 ⑤ 收敛；**对外以 DB 为准**。

### 4.3 信用规则引擎
- 触发点（点名、取消、局主取消、申诉裁决）只产生 `credit_log` 流水与事件；
- 结算 Job（开局结束后 24h）读取 `activity_member.status=爽约` 且 `credit_processed=0` 的成员 → 查 `credit_rule` → 扣分/写 log/置位（幂等）；
- 连续 3 次临取 → 生成 `user_punishment`（冻结报名 7 天）；等级每月 1 日重算（Job + 分布式锁）；
- 申诉：用户提交 → `complaint` 工单（type=信用申诉）→ 运营裁决 → 通过则插入反向 log（不覆盖原流水，保证审计完整）。

### 4.4 支付与退款（幂等 + 对账）
- 单号规范：`order_no=ACT+日期+随机`、`refund_no=RF+...`；表唯一索引 + 回调幂等（先查单状态，状态机只允许合法流转）；
- 支付成功回调：验签 → 查单 → `status: 支付中→成功` → 更新 member 已确认 → 发 `JoinConfirmedEvent`；
- 退款：`cancel-join` 事务内建 refund（处理中）→ 异步 Worker 调微信退款 → 成功置位 → 释放名额；失败指数退避重试 5 次 → 人工队列；
- 分账（V1.1）：启用微信服务商分账，收款进平台商户号后按 `settle_record` 分给局主；**平台不设余额，不滞留资金**；
- 每日对账 Job：本地订单 vs 微信账单（下载账单文件比对），差异单进异常表人工处理。

### 4.5 聊天（WebSocket 水平扩展）
```
用户 → Nginx(/ws 升级) → 任一 backend 实例
实例内连接存本地 Map；跨实例广播用 Redis Pub/Sub（频道 = activityId）
历史消息存 MySQL(chat_message)，进群只读拉取，游标翻页
权限：仅 activity_member 已确认成员可收发；退群/局结束 24h 转只读
```
> MVP 规模单实例即可；Redis Pub/Sub 广播为多实例预留，无需引入重型 IM。

### 4.6 通知管道
```
业务事件 ─→ RabbitMQ ─→ 通知 Worker
   ├─ 微信订阅消息（WxJava，token 缓存、失败重试）
   ├─ 站内 notification 表（角标轮询 30s）
   └─ App 推送（uni-push，V1.1）
```

### 4.7 附近检索与内容安全
- 附近局：写库时冗余 `geo_hash`（8 位 ≈ 38m×20m 精度）→ 列表先按 hash 前缀粗筛 + 距离精确过滤排序；Redis GEO 作为热点缓存；
- 内容审核：发布局/评价/昵称 → DFA 敏感词本地秒杀 → 云审核 API 异步复核 → 命中转人工或自动驳回。

### 4.8 金额与单位、时间
- 金额一律整数“分”，展示层转元；所有对外接口字段注释标明单位；
- 时间统一 `Asia/Shanghai`，DB 存本地时间（无时区换算需求的产品场景）；回调/日志打印 ISO8601。

## 5. 部署拓扑（docker-compose 阶段）

```
                    ┌──────────────────────────┐
  用户 ─ HTTPS ─▶ Nginx │ / → H5静态 · /admin → Web静态 │
                      │ /api → backend(8080)        │
                      │ /ws  → backend(升级WS)      │
                      └────────────┬───────────────┘
                                   │
                ┌──────────────────┼───────────────────┐
                ▼                  ▼                   ▼
          backend(:8080)    backend(:8080)      RabbitMQ(:5672)
                │  (2 实例起步)                    (延迟/事件)
                ▼                  ▼                   ▼
           MySQL(:3306)      Redis(:6379)         MinIO(:9000)
           (Flyway 管理)     (Lua/GEO/锁/缓存)     (头像/封面/聊天图片)
  可选：Prometheus + Grafana 监控 backend/metrics 与 MQ 队列深度
```

`.env` 管理敏感配置（密码/密钥）；Flyway 在启动时执行迁移；后端 `SPRING_PROFILES_ACTIVE=dev|test|prod`。

## 6. 非功能需求 → 技术手段对照

| PRD 非功能 | 技术手段 |
|---|---|
| 报名 P95 < 500ms | Redis 热路径 + 单行原子 UPDATE + 本地缓存类目/配置 |
| 名额强一致 | DB 原子 UPDATE + 唯一约束 + 对账 Job（见 4.2） |
| 支付/退款幂等 | 单号唯一 + 回调幂等 + Idempotency-Key（见 4.4） |
| 审计合规 | audit_log 全量 + credit_log 不可删改 + 运营操作 AOP |
| 内容合规 | DFA + 云审核 API + 举报工单闭环 |
| 可用性 | Compose 多副本 + Nginx 健康检查；MQ 失败重试 + 死信人工队列 |
| 多端一致 | 规则只在后端；前端按端做条件编译（地图/支付组件降级） |
| 可观测 | traceId 贯穿 + Prometheus 指标（接口 RT/名额冲突率/退款失败率/队列深度） |

## 7. 演进路线（当规模上来时）

| 阶段 | 触发信号 | 动作 |
|---|---|---|
| 用户 5w+ | 单表瓶颈 | MySQL 读写分离 + 热门局缓存；ES 接入搜索（标题/地点） |
| 事件量大 | MQ 积压 | RabbitMQ → RocketMQ（事务消息 + 顺序性）；延迟队列替代 ZSet |
| 团队 >2 个域团队 | 部署冲突 | 按 booking/payment/chat 拆服务；本地调用改 Feign + 分布式事务改 Saga/本地消息表 |
| App 活跃高 | 推送到达率 | 厂商推送通道接入（华为/小米/OPPO/vivo）+ 长连接收敛 |
| 合规要求 | 财务审计 | 对账系统独立服务 + 结算报表导出 |

## 8. 依赖与风险清单（选型层面）

| 风险 | 缓解 |
|---|---|
| uni-app 与 Web 双前端重复实现运营页 | 运营页只在 Web；C 端小程序为主，App/H5 仅保核心链路（信息架构已按此切分） |
| 微信类目/订阅消息审核 | 立项即准备《社区/工具类目资质与模板文案》，小程序提审前用真实业务场景演示 |
| 支付分账资质 | 第一版免费局 + 线下 AA 不碰资金；收费局走服务商分账且小范围灰度 |
| Sa-Token 相对小众 | 仅用于鉴权能力，占代码面小；若团队更熟 Spring Security 可直接替换（接口设计不受影响） |
| 自建 WS 网关的运维 | 单实例可承载 MVP；广播层已抽象，后期可整体替换为云厂商 IM 或 Netty 网关 |
